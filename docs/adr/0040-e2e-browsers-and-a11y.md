# ADR-0040: E2E を Firefox・WebKit・スマートフォンでも動かし、axe でアクセシビリティを検査する

- 状態: 採用
- 日付: 2026-11-15
- 関連: [ADR-0039](0039-quality-gates-in-ci.md)(CI の検査)、[ADR-0010](0010-editor-input.md)(編集の入力)、[ADR-0036](0036-quiet-paper-look.md)(スマートフォン表示)

## 状況

E2E は Chromium だけで動かしていた。利用者は、iPhone の Safari(WebKit)や Firefox でも開く。エディタは、隠した `textarea` で入力を受け、文字の位置を自分で計って描く(ADR-0010)。この作りは、ブラウザごとの違い(キーの扱い、選択、文字の幅、スクロール)が出やすい。

アクセシビリティも、機械では検査していなかった。名前のないボタンや、対比の足りない文字は、見た目では気付きにくい。

依頼者から、本番へ出す前に、CI で品質を担保したいという依頼があった(ADR-0039 の続き)。

## 決定

### ブラウザ

Playwright のプロジェクトを、次のようにする。

| プロジェクト  | ブラウザ               | 動かすテスト                                     |
| ------------- | ---------------------- | ------------------------------------------------ |
| chromium      | Chromium(デスクトップ) | すべて                                           |
| firefox       | Firefox                | `@chromium`、`@not-firefox` の付いたもの以外     |
| webkit        | WebKit(Safari)         | `@chromium` の付いたもの以外                     |
| mobile-chrome | Chromium(Pixel 7)      | 画面の作り、起動、ページの一覧、アクセシビリティ |
| mobile-safari | WebKit(iPhone 15)      | 同上                                             |

- Chromium にしかない機能を使うテストには、tag `@chromium` を付ける。いまは、日本語入力(開発者ツール用の通信 CDP で、IME のイベントを起こす)と、クリップボードの中身を読むテスト(読む許可を与えられるのが Chromium だけ)。
- Firefox で動かせない理由が、テストの側にあるもの(ブラウザの不具合など)には、tag `@not-firefox` を付け、テストの横に理由と Issue を書く。いまは、axe の検査(Playwright の Firefox で、axe を動かすと、ページの処理がときどき落ちる。落ちる画面と規則は、実行のたびに変わる。[#37](https://github.com/otomatty/amime/issues/37))。axe の検査の結果は、ブラウザのエンジンにはほとんどよらないので、Chromium と WebKit で確かめる。
- `test.skip` は使わない(規約で禁止している)。どのブラウザで動かすかは、設定ファイルの `grepInvert` で決める。
- CI では、E2E のジョブを、ブラウザのエンジンごとに3つ並べる(Chromium、Firefox、WebKit)。スマートフォンの設定は、同じエンジンのジョブで動かす。1つが落ちても、ほかは最後まで動かす(`fail-fast: false`)。
- 手元では、`pnpm test:e2e --project=chromium` のように、ブラウザを選べる。

### アクセシビリティ

- `@axe-core/playwright` で、主な画面(ログイン前のトップ、試し書き、プロジェクトの一覧、ページの一覧、記法を含むページと関連するページ、本文の検索結果、プロジェクトの設定、プロフィール)を検査する。
- 対象は WCAG 2.1 の A と AA の規則。違反が1つでもあれば落とす。
- 画面を足したら、この検査にも足す(規約)。

## 理由

- 同じテストを3つのエンジンで動かせば、ブラウザの違いによる壊れ方を、PR の段階で見つけられる。iPhone の Safari は WebKit なので、手元に iPhone がなくても、かなりの部分を確かめられる。
- スマートフォンの設定で、すべてのテストを動かすと時間がかかる。画面の作り(横にはみ出さない、ヘッダーが1段)と主な画面に絞る。
- axe は、導入した時点で、違反は0件だった。いまのうちに検査を入れておけば、増やさずに済む。

## 他の案

- **Firefox と WebKit を、週1回だけ動かす**: Actions の時間は減る。ただ、壊れたことに、マージの後で気付く。本番へ自動で出す(ADR-0037)ので、PR で止めたい。
- **Chromium にしかないテストを、`browserName` を見て、テストの中で抜ける**: 動かしていないのに「通った」と表示される。tag で、動かさないことを明示する。
- **アクセシビリティを、単体テスト(jsdom)で検査する**: jsdom では、色の対比や、実際の配置が分からない。実際のブラウザで検査する。

## 結果

- PR ごとの E2E のジョブは、1つから3つになる。並べて動かすので、待ち時間はあまり変わらない。Actions の使用時間は、1回の検査あたり、およそ10分増える(非公開のリポジトリでは、無料の枠から引かれる)。
- 日本語入力は、Firefox と WebKit では、まだ自動で確かめていない(CDP が使えないため)。実機で確かめる必要がある(feature-matrix の IME)。
- axe が見つけられるのは、機械で分かる違反だけ。スクリーンリーダーでの読み上げ(#3)は、別に確かめる。
- この開発環境では、Firefox と WebKit を入れられなかった。この2つは、PR の CI で初めて動く。
- 検索結果の画面の axe の検査で、結果が出る前に検査していた誤りを直したところ、語の印の上のリンクの文字の対比(4.4)が、AA の 4.5 に届いていないことが分かった。印の中のリンクは、濃いリンクの色(6.3)にした。
