# ADR-0016: 変更の種類と適用の規則、行IDの割り当て

- 状態: 採用(同じ行の同時編集の扱いは、実際の使い心地を見て見直す。取り消しで戻した行のIDの制約は [ADR-0019](0019-undo-own-edits.md) で解消)
- 日付: 2026-11-12
- 関連: [ADR-0006](0006-sync-model.md)(このADRが、変更の種類と適用の規則を置き換える)、[ADR-0005](0005-editor-architecture.md)、[ADR-0015](0015-outline-editing.md)

## 状況

ADR-0006 は、同期を「行IDを対象にした変更のコミット」で行うと決め、細部を P2 に残した。P2 を始めるにあたり、次の3つを決める必要がある。

1. 他の人の変更が先に入ったあとで届いたコミット(古い状態をもとに作られたコミット)を、どう扱うか。
2. 同じ行を2人が同時に変えたとき、どうなるか。
3. エディタの操作は本文の配列だけを扱っている(ADR-0005)。行IDを、どこでどう割り当てるか。

また、P1 で行やかたまりを動かす操作(ADR-0015)が入った。ADR-0006 は、行の移動を「削除と、新しいIDでの挿入」で表すとしていた。

## 決定

### 変更の種類

| 種類     | 内容                                                            |
| -------- | --------------------------------------------------------------- |
| `insert` | 新しい行を、指定した位置に入れる                                |
| `update` | 行の本文を置き換える                                            |
| `delete` | 行を消す                                                        |
| `move`   | 行を、IDと本文を保ったまま、指定した位置へ動かす(このADRで追加) |

`insert` と `move` の位置は、**前後2つの行**(`after` と `before`)で指す。次の順に決める。

1. `after` が null なら先頭。
2. `after` の行があれば、その直後。
3. `before` の行があれば、その直前。
4. どちらの行もなければ末尾。

### 適用は失敗しない

変更の適用(`applyChanges`)は、失敗しない。対象の行がなくなっている変更は、**その変更だけ**を捨て、残りを適用する。ADR-0006 の「適用できない変更を含むコミットは、全体を拒否する」は、これで置き換える。

| 場面                                          | 結果                           |
| --------------------------------------------- | ------------------------------ |
| `update` / `delete` / `move` の対象の行がない | 何もしない                     |
| `update` の本文が、いまの本文と同じ           | 何もしない                     |
| `insert` する行と同じIDの行が既にある         | 何もしない                     |
| `insert` / `move` の `after` の行がない       | 上の規則の 3・4 で位置を決める |
| `move` しても位置が変わらない                 | 何もしない                     |

適用の結果として、**実際に効いた変更**(`applied`)も返す。何も起きなかった変更は含まず、位置は実際に置いた場所の前後の行に書き直してある。適用する前と同じ文書に `applied` を適用すれば、同じ結果になる。

### 古い状態をもとにしたコミットの扱い

- サーバー(`PageDO`)は、コミットを届いた順に、**その時点の文書**へ上の規則で適用する。古い状態をもとにしたコミットも拒否しない。クライアントにやり直しを求めない。
- サーバーは、効いた変更(`applied`)を全員に配る。何も効かなかったコミットでは、バージョンを進めない。
- クライアントは「サーバーが確定した文書」と「まだ確定していない自分の変更」を分けて持つ。画面に出すのは、確定した文書に、自分の未確定の変更を同じ規則で適用したもの。他の人の変更が届いたら、確定した文書を進めてから、自分の未確定の変更を適用し直す。

クライアントが画面に出す文書は、サーバーがそのコミットを受け取ったときに計算する文書と、同じ関数・同じ入力で求まる。全員の画面は、サーバーが決めた順序に従って同じ内容になる(US-04)。クライアント側の仕組みは、保存とリアルタイム配信を入れるときに実装する。

### 同じ行への同時の変更

| 場面                                           | 結果                                             | 理由                                                                             |
| ---------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| 2人が同じ行の本文を変えた                      | あとからサーバーに届いたほうの本文になる(後勝ち) | 当面の扱い。行の中の文字単位の統合は、実際の使い心地を確かめてから決める         |
| 1人が行を消し、もう1人がその行の本文を変えた   | 行は消える(削除が勝つ)                           | 消した行が戻ると、消した側の意図に反する。位置を失った行を戻す場所も決められない |
| 1人が行を動かし、もう1人がその行の本文を変えた | 両方が生きる                                     | 行IDが変わらないので、互いに干渉しない                                           |
| 2人が同じ位置に行を入れた                      | 両方が入る。あとから届いたほうが上になる         |                                                                                  |

### 行IDの割り当て

エディタの操作(`@amime/editor-core`)は、これまでどおり本文の配列だけを扱う。行IDは、**編集の前後の本文を見比べて**割り当てる(`assignLineIds`)。

1. 上と下から見て、本文が変わっていない行は、そのまま。
2. あいだの行は、本文が完全に同じ行どうしを対応させる。行を並べ替えても、IDは本文についていく。
3. 残った行は、上から順に対応させる。行の中の編集、行の分割(上の行がIDを保つ)、結合(上の行のIDが残る)がこれにあたる。
4. 対応する行がなければ、新しいIDを付ける。

新しいIDは「端末ごとの接頭辞(乱数)-連番」で作る。端末だけで作れて、他の人のIDと重ならない。

編集の前後の文書から変更を求める関数(`diffLines`)は、並べ替えを `move` で表す。前からある行のうち、互いの順序が変わっていない最大の組は動かさず、残りだけを動かす。1行を遠くへ動かしても `move` は1つで済み、かたまりどうしの入れ替えでは行の少ないほうが動く。

## 理由(ユーザーストーリーから)

- **US-04**「別々の行への同時編集は、どちらも失われない」: コミット全体を拒否する方式では、1つの変更が他の人の変更とぶつかっただけで、同じコミットに入っていた無関係な行の変更まで失われる。変更を1つずつ判断すれば、ぶつかった変更だけが落ちる。
- **US-03 / US-04**: かたまりを動かす操作は日常的に使う。「削除と新しいIDでの挿入」で表すと、動かしている最中に他の人がその行に書いた内容が失われる。`move` でIDを保てば、両方が生きる。
- **US-05**「通信が切れている間の入力は、復帰後に送信される」: 復帰したときには、他の人の変更が先に入っている。古い状態をもとにしたコミットをそのまま受け付けられるので、再送が単純になる。
- **US-06**: 行IDが行の移動でも変わらないので、行ごとの履歴が移動で途切れない。

## 検討した他の案

| 案                                                     | 採用しなかった理由                                                                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 古いコミットを拒否し、クライアントが作り直して送り直す | 往復が1回増える。書き込みが多いページでは、送り直しが何度も続くことがある                                                            |
| エディタのすべての操作に行IDを通す                     | 操作ごとに「どの行がIDを保つか」を書くことになり、操作を足すたびに間違えやすい。本文だけを扱う純粋な関数という単純さ(ADR-0005)を失う |
| 位置を1つの行だけで指す(ADR-0006 の `before`)          | その行を他の人が消していると、行を置く場所が末尾しかなくなる                                                                         |
| 行の中を文字単位で統合する(OT、CRDT)                   | ADR-0006 のとおり。同じ行の同時編集に限って必要になるので、必要になった時点で、その部分だけを足す                                    |

## わかっている制約

- 削除を取り消して戻した行には、新しいIDが付く(取り消しは文書全体の状態を戻す方式のため。ADR-0014 のとおり、P2 で変更を打ち消す方式に置き換える)。
- 同じ本文の行が複数あると、並べ替えたときにどの行がどのIDを引き継ぐかは「上から順」になる。本文が同じなので、見た目には違いが出ない。
- 自分が書いている行を、同時に他の人が消すと、書いた内容は残らない。

## まだ決めていないこと

ADR-0006 の「P2で決めること」のうち、行の並び順の保存方法、WebSocket と再接続、入力の検証は、保存とリアルタイム配信を実装するときに、それぞれ ADR に記録する。
