# ADR-0006: 同期は行IDを使ったコミット方式にする

- 状態: 採用(コミットの競合解決は P2 で詳細を決める)
- 日付: 2026-11-11

## 状況

同じページを複数人が同時に編集する(US-04)。通信が切れても入力を失わない(US-05)。行ごとの更新者と履歴を見たい(US-06)。

## 決定

- すべての行に不変のID(`LineId`)を振る。
- 変更は、行IDを対象にした3種類の操作で表す: `insert`(指定した行の前、または末尾に挿入)、`update`(本文の置き換え)、`delete`。
- クライアントは変更の列を「コミット」として送る。`PageDO` が受け取った順に適用し、ページのバージョンを1つ進めて、全員に配信する。
- 変更の表現と適用の規則は `packages/sync` に置き、クライアントとサーバーで同じコードを使う。
- 適用できない変更を含むコミットは、全体を拒否する(一部だけ適用しない)。

### P0で実装した範囲

- `applyChanges` と `diffLines`、およびその往復の性質のプロパティテスト。
- `PageDO` の `getPage` と `commit`(RPC)。保存は SQLite。
- 現在の `commit` は全行を書き直す。行数に比例する処理なので、P2で差分だけを書く方式に置き換える。

### P2で決めること

- コミットの基準バージョンと、古い基準で届いたコミットの扱い(サーバーでの組み替えか、クライアントでのやり直しか)。
- 同じ行を2人が同時に書き換えた場合の扱い(後勝ちか、行内の文字単位の統合か)。
- 行の並び順の保存方法(連番か、間に挿入できる順序キーか)。
- WebSocket の休止(Hibernation)、再接続時の差分の取得、未送信コミットの端末内保存。
- 入力の検証(スキーマ)と認可。

## 理由(ユーザーストーリーから)

- **US-06**: 行IDがあると、行ごとの作成者・更新者・更新時刻、行へのリンクを自然に持てる。
- **US-04**: 編集の多くは別々の行で起きる。行単位の操作にすると、別の行への変更どうしは順序に関係なく両立し、競合の範囲が同じ行に限られる。
- **US-05**: コミットは小さく独立しているので、未送信分を端末に貯めて再送する実装が単純になる。

## 検討した他の案

| 案             | 採用しなかった理由                                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CRDT(Yjs など) | 文字単位の統合に強く、オフライン編集も得意。ただし行IDや行ごとの履歴とは別の仕組みになり、保存データが大きくなる。順序を決められるサーバー(Durable Object)がある構成では、利点を使い切れない |
| 文字単位のOT   | 実装と検証の費用が高い。行単位で足りない場面は同じ行の同時編集に限られるので、そこだけ補えばよい                                                                                             |

## 影響

- 同じ行の同時編集は、文字単位の方式より粗い結果になり得る。P2で扱いを決め、テストで固定する。
- 行の移動は「削除と、新しいIDでの挿入」になる。移動で行IDを保ちたくなった場合は `move` 操作を追加する。
