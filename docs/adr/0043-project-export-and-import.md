# ADR-0043: プロジェクトを、1つのファイルに書き出し、読み込めるようにする

- 状態: 採用
- 日付: 2026-11-17
- 関連: [US-14](../user-stories/README.md)(データを持ち出せる)、[ADR-0002](0002-scope-and-non-goals.md)(本家との互換は不要)、[ADR-0024](0024-page-identity-and-project-index.md)(ページのIDと台帳)、[ADR-0032](0032-login-and-sessions.md)〜[ADR-0034](0034-invites-and-members.md)(権限)

## 状況

Tsuzuri は本番で使われ始めた。プロジェクトの全ページを、手元に持っておく手段がない。誤って消したときに戻せず、別のプロジェクトへ移すこともできない(US-14)。

ページの本文は、ページごとの Durable Object(PageDO)にある。台帳(ProjectDO)も本文を写しているが、本文を探すための写しで、長いページは途中までしかない(ADR-0031)。バックアップには使えない。

## 決定

### ファイルの形式

独自の形式の JSON にする(本家との互換は不要。ADR-0002)。

```json
{
	"format": "tsuzuri-project",
	"version": 1,
	"project": "notes",
	"exportedAt": "2026-11-17T01:02:03.000Z",
	"pages": [
		{
			"title": "買い物",
			"lines": ["買い物", "牛乳"],
			"pinned": false,
			"created": 1794878254583,
			"updated": 1794878254608
		}
	]
}
```

- ページは、名前と、すべての行の本文、一覧の先頭に固定していたか、作った時刻と最後に変えた時刻を持つ。作った順に並べる。
- 行IDは入れない。読み込むときに、新しく付ける。
- `format` で、このアプリのファイルかを見分ける。形を変えるときは `version` を上げ、古い版も読めるようにする。読めない版(新しい版)は、そう知らせる。
- 1ページでも形が違えば(1行目と名前が違う、行の中に改行がある、行が長すぎる、など)、ファイルごと読み込まない。どこまで復元したかが分かりにくくなるため。
- 作った時刻と変えた時刻は、記録のために入れる。読み込んだページは、読み込んだ時刻に作ったものになる。

判定は `packages/sync` の純粋関数(`buildProjectFile`、`parseProjectFile`、`insertionCommits`)にする。

### 書き出しと読み込みは、画面から、いつものAPIで行う

新しいAPIは作らない。

- **書き出し**: 一覧(作った順)を最後までたどり、それぞれのページの本文を読み、ファイルにしてブラウザに保存させる。4ページずつ並べて読む。1ページでも読めなければ、途中までのファイルにせず、失敗を知らせる(足りないバックアップを作らない)。
- **読み込み**: ページごとに、名前で開き(台帳がIDを決める)、本文が空なら、すべての行を送る(1回のコミットの変更の数の上限ごとに分ける)。固定していたページは、固定する。1ページずつ行う。
- **同じ名前のページがあれば、書き換えずに飛ばす。** 読み込みで、いまのページを失わない。結果に、作ったページ、飛ばしたページ、送れなかったページの名前を出す。もう一度読み込むと、まだないページだけを作る。

### だれが使えるか

- 書き出しは、プロジェクトのメンバー(管理者とメンバー)。設定の画面に出す。
- 読み込みは、管理者だけ(画面に出すのを、管理者だけにする)。

## 理由

- 書き出しをサーバーの中で行うと、1回の要求の中で、ページの数だけ Durable Object を呼ぶ。Workers には、1回の要求の中で出せる要求の数に上限がある。画面から1ページずつ読めば、この上限にかからず、ページが多くても進み具合を出せる。
- いつものAPIを使うので、ログインの状態とプロジェクトの権限は、それぞれのAPIが、これまでどおり確かめる(ADR-0032〜0034)。新しい穴を作らない。
- 同じ名前を飛ばすのは、読み込みを、いつでも安全にやり直せるようにするため。上書きは、元に戻せない。
- 読み込みを1つずつにするのは、ファイルの中に名前の重なるページがあったときに、同じページへ2回書き込まないため。

## 他の案

- **サーバーに、書き出しと読み込みのAPIを作る**: 1回の要求で済むが、上の上限にかかる。ページの多いプロジェクトでは、途中で失敗する。
- **台帳の本文の写しから書き出す**: 1回の呼び出しで済むが、長いページは途中までしかない。
- **同じ名前のページを、上書きする(または「名前 (2)」として作る)**: 上書きは、いまの本文を失う。別の名前で作ると、読み込むたびにページが増える。必要になったら、選べるようにする。
- **本家の形式**: 互換は不要との回答(ADR-0002)。

## 結果

- 読み込みの権限は、画面で分けているだけで、サーバーは分けていない。読み込みは「ページを作る」ことの繰り返しなので、メンバーなら、もともとできる操作である。
- 保存した直後のページは、一覧(台帳)に載るまでの数秒のあいだ、書き出しに入らない。
- ページの多いプロジェクトでは、書き出しと読み込みに時間がかかる(ページごとに1〜3回の要求)。進み具合を出す。
- 履歴(ページの変更の記録)と、メンバー、招待リンクは、書き出さない。
- 画像のアップロード(US-13)を入れたら、画像をどう書き出すかを、改めて決める。
