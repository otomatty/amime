# ADR-0037: CI と Deploy を分け、main に入った変更を本番へ自動で出す

- 状態: 採用(実際の Cloudflare アカウントへのデプロイは、未確認)
- 日付: 2026-11-14
- 関連: [ADR-0008](0008-tdd-and-ci.md)(CIでの検査)、[ADR-0003](0003-platform-cloudflare.md)(Cloudflare と `cf`)、[ADR-0032](0032-login-and-sessions.md)(ログインに使うシークレット)

## 状況

検査とデプロイは、1つのワークフロー(`ci.yml`)に入っていた(ADR-0008)。デプロイは、リポジトリ変数 `DEPLOY_ENABLED` で、PRのプレビューと本番の両方が、まとめて有効になる作りだった。

P4 でログインと権限が入り、公開してよい状態になった。依頼者から、Cloudflare へ自動でデプロイできるようにしたい、という依頼があった。

まとめて有効にすると、困ることがある。

- Dependabot のPRには、シークレットが渡らない。プレビューのデプロイが、毎回失敗する。
- プレビュー環境では、ログインできない(ADR-0032)。見られるのは、ログインしていないときの画面だけ。プレビューが、本番と同じデータにつながるかどうかも、確かめていない。
- デプロイが失敗したのか、検査が失敗したのかが、ワークフローの名前から分からない。

## 決定

### ワークフローを、2つに分ける

- **CI(`ci.yml`)**: PRごとの検査。ほかのワークフローからも呼べるようにする(`workflow_call`)。
- **Deploy(`deploy.yml`)**: `main` に入ったとき(と、手動)に動く。CI を呼んで、同じ検査を `main` の内容で行い、通ったら、本番へデプロイする。

`main` での検査は、Deploy の中でだけ行う(CI は、`main` への push では動かさない。同じ検査を、2回行わない)。PRでの検査の名前は、変わらない(ブランチ保護の設定は、そのまま使える)。

### 本番へのデプロイ

- リポジトリ変数 `DEPLOY_ENABLED` が `true` のときだけ行う。`main` 以外からは、手動でも出さない。
- 1つずつ順に行い、途中のものを取り消さない。
- **`main` の先頭のコミットのときだけ、出す。** 検査に時間がかかっているあいだに、もっと新しいコミットが入り、先に本番へ出ていることがある(push と手動が重なったときなど)。古いコミットで、新しいものを上書きしない。古い実行を、あとからやり直したときも、出さない。
- 先に、Cloudflare に入るための値(`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`)があるかを確かめ、なければ、理由を出して止める。
- ログインとプロジェクトの設定(`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`PROJECT_CREATORS`)は、なくてもデプロイする(その機能が、使えないままになる)。ないことは、注意として出す。
- Cloudflare の側でも、どのコミットを出したかが分かるように、バージョンに、印(コミットの先頭12文字)と件名を付ける。
- 出したあと、本番のURL(リポジトリ変数 `APP_URL`)の `/api/health` が応えるかを確かめる。`APP_URL` がなければ、確かめずに、そのことを知らせる(最初のデプロイの前には、URLが分からない)。
- 手動でも動かせる(`workflow_dispatch`)。シークレットは、デプロイのときに Worker へ渡るので、登録し直したあとに、出し直すのに使う。

### プレビュー環境は、別の変数で、既定では無効にする

- リポジトリ変数 `PREVIEW_ENABLED` が `true` のときだけ、PRの検査のあとに、プレビュー環境へデプロイする。
- フォークと Dependabot のPRは、対象にしない。

## 検討した他の案

- **`workflow_run` で、CI の成功を受けて Deploy を動かす**: CI と Deploy が、別々の実行になる。どの検査の結果で出したのかが、たどりにくい。`workflow_run` は、既定のブランチにあるワークフローの内容で動くので、ワークフローを変えるPRの確かめ方も、分かりにくくなる。
- **Cloudflare の側で、リポジトリとつないで、自動でビルドさせる**(Workers Builds): 検査を通ってから出す、という順序を、こちらで決められない。`cf` のベータ版での対応も、確かめていない。
- **1つのワークフローのまま、変数を増やす**: 動くが、失敗したときに、検査とデプロイのどちらなのかが、名前から分からない。

## わかっている制約

- 実際の Cloudflare アカウントへのデプロイは、まだ一度も行っていない。確かめたのは、ビルド、`cf deploy --dry-run`(印と件名を付けた形)、各手順のシェルを手元で動かすこと、まで。
- `cf` の公式文書(CI での使い方、APIトークンの権限)を、この変更のときには、開けなかった。`cf` の `--help`、同梱の README、設定の型の説明から書いている。APIトークンに要る権限は、Wrangler での経験からの見立て。
- D1 のデータベースが、最初のデプロイで自動で作られること(`--provision`)は、未確認。
- デプロイを前のバージョンに戻す手順は、用意していない(Cloudflare のダッシュボードから戻せるが、Durable Object や D1 のデータは戻らない)。
- 閉じたPRのプレビューを消す仕組みは、ない。
