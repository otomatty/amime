# ADR-0001: 設計判断をADRに記録し、矛盾は優先順位で解く

- 状態: 採用
- 日付: 2026-11-11

## 状況

このプロジェクトは、開発者(AI)がオーナーとして判断を下し、依頼者が方向を決める体制で進める。セッションをまたぐと判断の経緯が失われやすい。また「完全再現」という目標は、法的制約、基盤の制約、段階的な開発と衝突する場面が多い。

## 決定

1. 設計判断は `docs/adr/NNNN-題名.md` に記録する。採用後のADRは書き換えず、変更するときは新しいADRで置き換える。
2. 情報が食い違ったときの優先順位を固定する: 法的・安全上の制約 > ユーザーストーリー > ADR > テスト > コード > コメント。
3. 判断の担当を可逆性で分ける。後から戻せる技術判断は開発者が決めて記録する。費用・公開範囲・外部アカウント・法務に関わる判断は依頼者に確認する。
4. 決着した内容は、テストか Lint ルールとして実装する。

手順の詳細は [conventions.md](../conventions.md) の「判断の優先順位と矛盾の解き方」に置く。

## 理由

- 優先順位が決まっていれば、矛盾を見つけた人がその場で直す対象を判断できる。
- ADRを書き換えない運用にすると、「なぜ以前はそうだったか」が残り、同じ議論を繰り返さずに済む。
- 可逆な判断まで確認を取ると開発が止まり、不可逆な判断を独断すると依頼者の意図から外れる。可逆性は両者を分ける基準として単純で、迷いが少ない。

## 最初に解消した矛盾

| 矛盾                                                | 解消                                                                 | 記録              |
| --------------------------------------------------- | -------------------------------------------------------------------- | ----------------- |
| 「完全再現」と商標・著作権                          | 機能・記法・操作感を再現し、名称・デザイン・文言・コードは独自にする | ADR-0002          |
| 「完全再現」と Cloudflare の制約                    | 通信方式は再現せず、利用者から見える挙動を再現する                   | ADR-0002, 0006    |
| 「完全再現」と「先に基盤を作る」                    | フェーズに分け、再現度を機能一覧表で計測する                         | feature-matrix.md |
| 「オーナーは開発者」と「不明点は質問する」          | 可逆性で担当を分ける                                                 | 本ADR             |
| TDD と「本家の仕様が非公開」                        | 公開ヘルプと観察した挙動を例としてテストにする                       | ADR-0008          |
| 提案時の構成(apps/web と apps/worker)と `cf` の制約 | デプロイ単位を1つにまとめ、境界は Lint で守る                        | ADR-0004          |
