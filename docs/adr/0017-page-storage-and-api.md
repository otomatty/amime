# ADR-0017: ページの保存方法、API、保存の進め方

- 状態: 採用(リアルタイム配信は [ADR-0018](0018-realtime-delivery.md)、端末内への未送信分の保存は [ADR-0020](0020-pending-changes-on-device.md) で追加。送信に失敗したときの扱いは [ADR-0021](0021-commit-ids.md) で置き換え)
- 日付: 2026-11-12
- 関連: [ADR-0006](0006-sync-model.md)、[ADR-0009](0009-auth-and-access.md)、[ADR-0016](0016-changes-and-line-ids.md)、[ADR-0014](0014-selection-clipboard-undo.md)

## 状況

変更の種類と適用の規則は ADR-0016 で決めた。このADRでは、ページを実際に保存して読み込むために必要な残りを決める。ADR-0006 の「P2で決めること」のうち、行の並び順の保存方法と入力の検証がここに入る。

ADR-0009 は、認証(P4)が入るまで、書き込みできるAPIを公開環境に置かないと決めている。

## 決定

### 行の並び順は「順序キー」で保存する

- `PageDO` は、行ごとに順序キー(文字列)を持つ。行は、順序キーの順に並ぶ。
- 2つの行のあいだに行を入れるときは、2つのキーのあいだに入るキーを作る。他の行は書き換えない。
- コミットでは、実際に効いた変更(`applied`)の対象の行だけを書き込む。P0 の「全行の書き直し」をやめる。
- 順序キーはサーバーの中だけで使う。クライアントは位置を前後の行で指す(ADR-0016)ので、キーを知らない。あとでキーの作り方を変えたり、振り直したりしても、クライアントに影響しない。
- キーの生成には `fractional-indexing`(CC0)を使う。

### API

| メソッドとパス                  | 内容                                                                        |
| ------------------------------- | --------------------------------------------------------------------------- |
| `GET /api/pages/:name`          | ページを返す(`{ version, lines }`)。まだないページは、バージョン0で行がない |
| `POST /api/pages/:name/commits` | 変更を適用する(`{ changes }` → `{ version, applied }`)                      |

- ページは、正規化した名前(`toTitleLc`。空白と大文字小文字の違いは同じページ)で識別する。プロジェクト(P4)が入るまで、プロジェクトは1つだけとする。
- 入力は `@amime/sync` のスキーマ(`valibot`)で検査する。クライアントも、同じスキーマでサーバーの応答を検査する。

| 上限                    | 値                              |
| ----------------------- | ------------------------------- |
| 1行の本文               | 20,000 文字(改行を含まない)     |
| 1つのコミットの変更の数 | 2,000                           |
| コミットの本文の大きさ  | 2 MiB                           |
| ページ名                | 200 文字                        |
| 行ID                    | 英数字・`_`・`-` で 64 文字まで |

### 認証が入るまで、公開環境ではAPIを無効にする

- Worker に `PAGE_API` という値を渡し、`enabled` のときだけページのAPIが応答する。それ以外は、読み込みも書き込みも 403 を返す。
- 値は `cloudflare.config.ts` で、モードから決める。`enabled` になるのは `development`(手元での開発)、`test`(サーバーのテスト)、`e2e`(E2Eテスト用のビルド)だけ。**一覧にないモードでは無効**なので、本番(`production`)、プレビュー環境、モードの指定がない場合はすべて無効になる。
- E2Eテストは、`--mode e2e` でビルドした成果物に対して実行する(`pnpm test:e2e` が先にビルドする)。
- 公開環境で保存を試したい場合は、Cloudflare Access などでデプロイ先を保護したうえで、そのモードを一覧に足す。これは公開範囲に関わるので、依頼者に確認してから行う。

### クライアントの保存の進め方

状態の持ち方と規則は `@amime/sync` のセッションにある(ADR-0016 の「確定した文書」と「画面の文書」)。画面側は「いつ送るか」だけを決める。

- 最後の編集から 0.3 秒待って保存する。続けて打っているあいだは送らない。
- 1度に送るコミットは1つ。送る変更は、確定した文書と画面の文書の差分。保存中に書き足した分は、応答を受け取りしだい続けて送る。
- 応答のバージョンが期待より進んでいたら、他の人の変更が先に入っている。ページを読み直して確定した文書とし、まだ送っていない編集をその上に載せ直す。
- 保存に失敗したら、1秒から最大30秒まで間隔を延ばしながら再試行する。通信が戻ったこと(`online`)を検知したら、すぐに試す。
- 送信に失敗すると、その変更がサーバーに入ったかどうかは分からない(応答だけが届かなかったのかもしれない)。再試行では、先にページを読み直し、前の確定した文書からの自分の変更をすべて載せ直す。サーバーに入っていた変更は、もう一度適用しても何も起こさない(ADR-0016)ので、二重にならない。行方が分かるまでは「保存済み」と表示しない。
- 差分が1つのコミットに収まらないとき(変更が 2,000 を超える、本文の合計が 30 万文字を超える)は、先頭から収まる分だけを送り、残りを続けて送る。差分は上から順に適用できる並びなので、途中までを先に送っても正しく適用できる。
- サーバーが内容を断ったとき(400、413。長すぎる行など)は、同じ内容を送り直さない。保存できないことと直し方を画面に出し、内容が直されたら、もう一度保存する。
- 未保存の変更があるあいだは、保存の状態を画面に出し、ページを離れる前にブラウザの確認を出す。

### 画面

| 場面                     | 挙動                                                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トップ(`/`)              | 保存されない試し書きのページ。P3 でページの一覧に置き換える                                                                                                                |
| それ以外のパス           | パスの最後の部分をページ名として、そのページを開く。手前の部分は、プロジェクト(P4)が入るまで使わない(ページの中のリンクは `./ページ名` なので、同じ規則でリンク先が決まる) |
| まだないページを開いた   | ページ名(`_` は空白に戻す)を1行目に入れて始める。最初に表示した内容のままなら保存しない(開いただけではページを作らない。書いてから取り消して元に戻した場合も同じ)          |
| 他の人の変更を取り込んだ | 画面の文書を置き換える。カーソルは同じ行についていく。取り消しの履歴は捨てる                                                                                               |

取り消しの履歴を捨てるのは、いまの取り消しが文書全体を巻き戻す方式で、他の人の変更まで巻き戻してしまうためである(ADR-0014)。変更を打ち消す方式に置き換えたら、履歴を保てる。

## 理由(ユーザーストーリーから)

- **US-05**「サーバーが受け付けた変更は、再起動後も残っている」: 保存はコミットごとにトランザクションで行う。`PageDO` がメモリから追い出されても、保存した内容から復元できることをテストで固定した。
- **US-05**「未保存の変更があることが、画面で分かる」「通信が切れている間の入力は、復帰後に送信される」: 保存の状態を常に表示し、失敗しても書き続けられ、自動で再試行する。
- **US-04**「別々の行への同時編集は、どちらも失われない」: 他の人の変更が先に入っていても、読み直して自分の編集を載せ直すので、どちらも残る。
- 行の多いページでも、1文字の編集で書き込むのは1行だけにしたい。順序キーなら、行の挿入でも他の行を書き換えずに済む。

## 検討した他の案

| 案                                | 採用しなかった理由                                                                                        |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 並び順を連番で持つ                | 行を入れるたびに、後ろの行をすべて書き換えることになる                                                    |
| 順序キーの生成を自作する          | 末尾への追加を繰り返したときにキーを短く保つなど、考慮点が多い。広く使われている実装を使うほうが確実      |
| 入力の検査を手書きする            | 変更の種類が増えるたびに検査とテストを書き足すことになり、漏れやすい。スキーマなら型と検査が1か所で決まる |
| ビルド時にAPIのコードごと取り除く | 設定の誤りに気づきにくい。実行時に 403 を返すほうが、無効であることを外から確かめられる                   |
| 編集のたびにすぐ送る              | 1文字ごとにコミットが作られ、通信と書き込みが増える。0.3 秒の待ちなら、保存の遅れとして気にならない       |

## わかっている制約

- **他の人の変更は、自分が保存するときに初めて画面に入る。** リアルタイム配信(WebSocket)は次の実装で入れる。
- タブを閉じると、まだ送っていない変更は失われる(離れる前に確認は出る)。未送信分を端末内に保存する仕組みは、まだない。
- コミットのたびに、ページの全行を読み込んでから適用している(書き込みは差分だけ)。行数の上限と、メモリに持つかどうかは、リアルタイム配信を入れるときに決める。
- 同じ場所への挿入を繰り返すと、順序キーが少しずつ長くなる。キーの振り直しは、必要になった時点で入れる。
- 1行が 20,000 文字を超えると保存できない(画面に直し方を出す)。編集欄の側では、長さを制限していない。
- 応答が届かなかった送信のあとで、その変更を取り消して元に戻していた場合、取り消すつもりだったかどうかを判断できないので、読み直したあとの画面はサーバーの内容になる(送った変更が入っていれば、それが画面に戻る)。コミットに識別子を付けてサーバーで照合すれば区別できるが、まれな場面なので入れていない。
- P0 の `PageDO` が使っていた `lines` テーブルからの移行は行わない。P0 の時点でページを書き込む経路はテストだけで、どの環境にも保存されたページがないため。今後の保存形式の変更では、古い形式を読めるようにする([デプロイの注意](../deploy.md))。
