# ADR-0010: エディタの入力処理と、日本語入力の検証結果

- 状態: 採用(実機での日本語入力の確認が残っている)
- 日付: 2026-11-12
- 関連: [ADR-0005](0005-editor-architecture.md) の「P1の最初に検証する」への回答

## 状況

ADR-0005 で、エディタを自前の行指向モデルで作ると決めた。最大のリスクは日本語入力(IME)で、P1の最初に検証することにしていた。

## 決定

### 入力の受け取り方

- 文字入力は、画面に見えない `textarea` で受け取る。表示は自前で描画する。
- **確定した文字列の出どころを `textarea` の値だけにする。** `input` と `compositionend` のどちらでも「`textarea` の値を取り出して挿入し、空にする」という同じ処理を呼ぶ。変換中の `input` では何もしない。
  - `input` と `compositionend` の発火順はブラウザによって違う。イベントが運ぶ文字列(`event.data`)を使うと、順序によって二重に挿入するか取りこぼす。値を取り出して空にする方式なら、どちらの順序でも1回だけ挿入される。
- 変換中の文字列は `compositionupdate` の値を使い、カーソルの直前に下線付きで自前で描画する。行のデータには入れない。
- 変換中のキー操作は扱わない。`isComposing` に加えて `keyCode === 229` も変換中とみなす。Safari は、確定に使った Enter を変換終了の後に `keyCode` 229 で通知するためである。
- `textarea` はカーソルの位置に重ねる。変換候補のウィンドウが、ブラウザによって `textarea` の位置を基準に表示されるためである。

### 描画

- 行は、利用者から見た1文字(書記素)ごとの要素として描画し、各要素に文字位置を持たせる。クリックされた要素から、カーソルの移動先を求める。
- カーソルは、幅のない要素を文字の間に置いて表す。位置の計算が不要で、折り返しや絵文字があってもずれない。
- 行頭の空白は文字として表示せず、1段ぶんの幅の要素にする。折り返した行は、インデントの位置で揃える。

### 文字の単位

- カーソル移動と削除は、書記素の単位で行う(`Intl.Segmenter`)。絵文字や結合文字が途中で壊れない。
- 文字位置は UTF-16 の単位で数える。ブラウザのAPIやJavaScriptの文字列操作と同じ単位にそろえるためである。

### ADR-0007 からの変更

コンポーネントテストの実行環境を happy-dom から jsdom に変えた。happy-dom の `CompositionEvent` は変換中の文字列(`data`)を運ばず、日本語入力のテストが書けなかったためである。

## 検証した内容

| 項目                                                   | 方法                                | 結果 |
| ------------------------------------------------------ | ----------------------------------- | ---- |
| 変換中の文字列がカーソル位置に表示され、行には入らない | コンポーネントテスト、E2E           | 通過 |
| 確定で1回だけ挿入される(`input` が先の順序)            | コンポーネントテスト、E2E(Chromium) | 通過 |
| 確定で1回だけ挿入される(`input` が後の順序)            | コンポーネントテスト                | 通過 |
| 変換の取り消しで何も入らない                           | コンポーネントテスト、E2E           | 通過 |
| 変換中の Enter で改行しない                            | コンポーネントテスト                | 通過 |
| 確定のあと続けて入力・変換できる                       | E2E                                 | 通過 |
| `textarea` がカーソルの位置に重なっている              | E2E                                 | 通過 |

E2Eでは、Chromium の開発者ツール用の通信(CDP)の `Input.imeSetComposition` と `Input.insertText` で、IMEと同じイベント列を発生させている。

## 検証できていないこと

自動テストはイベントの列を再現しているだけで、実際のIMEを動かしてはいない。次の項目は、人が実機で確認する必要がある。

- macOS(日本語IM、Google 日本語入力)、Windows(Microsoft IME)での変換・確定・取り消し
- 変換候補のウィンドウが、カーソルの近くに表示されること
- Safari と Firefox での動作(発火順の違いはコンポーネントテストで再現しているが、実ブラウザでは未実行)
- iOS / Android のソフトウェアキーボード(予測変換、フリック入力)

実機で解決できない問題が見つかった場合は、ADR-0005 に書いたとおり、描画と入力の層だけを CodeMirror 6 に置き換える。

## 影響

- Tab キーをインデントに使うため、キーボードだけでエディタの外へフォーカスを移す手段が別に必要になる(P6でアクセシビリティとあわせて検討する)。
- 文字ごとに要素を作るため、非常に長い行では描画が重くなる可能性がある。問題が出た時点で、カーソルのある行だけを文字単位にする最適化を検討する。
- 上下のカーソル移動は文字数を基準にしている。等幅でないフォントでは見た目の位置とずれるため、見た目の横位置に合わせる改善が必要である(feature-matrix.md)。
