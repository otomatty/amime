# ADR-0018: 他の人の変更の配信(WebSocket)

- 状態: 採用(Cloudflare 上での動作は未確認。手元の Workers ランタイムで確認した。取り消しの履歴が消える制約は [ADR-0019](0019-undo-own-edits.md) で解消)
- 日付: 2026-11-12
- 関連: [ADR-0006](0006-sync-model.md)、[ADR-0016](0016-changes-and-line-ids.md)、[ADR-0017](0017-page-storage-and-api.md)(「他の人の変更は、自分が保存するときに初めて画面に入る」という制約を、このADRで解消する)

## 状況

ページの保存と読み込みはできるようになった(ADR-0017)が、他の人の変更は、自分が保存するときにしか画面に入らない。US-04 は「他の人の編集が、再読み込みなしで1秒以内に反映される」ことを求めている。

## 決定

### 保存は HTTP、配信は WebSocket

- 保存(コミット)は、これまでどおり HTTP で送る。
- WebSocket は、サーバーからクライアントへ「他の端末のコミット」を届けるためだけに使う。クライアントからは、接続の確認(ping)しか送らない。

### サーバー

- 接続は、ページごとの `PageDO` が持つ。`GET /api/pages/:name/socket?client=<端末の識別子>` で接続する。認証が入るまで、ページのAPIと同じく公開環境では無効(ADR-0017)。
- 接続は、休止に対応した方式(WebSocket Hibernation API)で受け付ける。やりとりがないあいだ、`PageDO` は接続を保ったままメモリから降ろされる。`PageDO` はメモリに状態を持たない(ADR-0017)ので、休止から戻っても、そのまま配信できる。
- コミットが効いたら、保存してから、接続している端末に配信する。何も効かなかったコミットは配信しない。
- **送った本人には配信しない。** 本人は HTTP の応答で結果を受け取る。同じコミットが2つの経路で届くと、どちらが先に着くかで処理が分かれてしまうためである。端末の識別子(タブごとの乱数)をコミットと接続の両方に付けて、本人の接続を見分ける。
- `ping` には、`PageDO` を起こさずに `pong` を返す(自動応答)。それ以外のメッセージを送ってきた接続は閉じる。
- **他のサイトのページからの要求は断る。** ページのAPI(WebSocket の接続を含む)は、`Origin` が付いていて、それが要求を受けたサイトと違えば 403 を返す。WebSocket は他のサイトからでも接続でき、書き込みも形式によっては送れてしまうためである。手元の開発環境でも、開いている他のサイトから読み書きされないようにする。

| サーバーが送るメッセージ               | 内容                                                         |
| -------------------------------------- | ------------------------------------------------------------ |
| `{ type: "hello", version }`           | 接続した直後に送る。いまのバージョン                         |
| `{ type: "commit", version, applied }` | 他の端末のコミットが効いた。適用後のバージョンと、効いた変更 |

### クライアント

届いたコミットは、バージョンで扱いを決める。規則は `@amime/sync` のセッションにある。

| 届いたコミットのバージョン    | 扱い                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| 自分の持つバージョンの次      | 確定した文書に適用し、画面の文書を作り直す(送信中の変更と、まだ送っていない編集を載せ直す) |
| 自分の持つバージョン以下      | 無視する(既に、読み直しなどで反映してある)                                                 |
| 2つ以上先(あいだが抜けている) | 適用しない。ページを読み直して追いつく                                                     |

- 接続したとき(`hello`)に、サーバーのバージョンのほうが進んでいたら、読み直して追いつく。切れているあいだのコミットは届かないので、つなぎ直すたびにこれで追いつく。
- 「サーバーにあると分かっている、いちばん新しいバージョン」を覚えておき、自分の持つバージョンがそこに届くまで読み直す。読み直しの応答を待っているあいだに、さらに先のコミットがあると分かることがあるためである。読み直したページのほうが古ければ(配信で先まで進んでいたら)、そのページは使わない。文書とバージョンを巻き戻さない。
- 保存の応答を待っているあいだに他の人のコミットが届いたら、送信中の状態はそのままにして取り込む。あとから届く応答は、そのまま反映できる。逆の順(応答が先)なら、応答のバージョンが飛んでいるので、読み直す(ADR-0017)。
- 接続が切れたら、1秒から最大30秒まで間隔を延ばしながらつなぎ直す。30秒ごとに `ping` を送り、次の確認までに `pong` が返らなければ、切れたものとして扱う。

### 編集欄と保存の側は、いつも同じ文書を見る

- 編集欄の状態は、操作を受け取った**その場で**進める(描画を待たない)。編集後の文書も、その場で保存の側に知らせる。
- 他の人の変更を取り込んだ文書は、その場で編集欄に渡し、編集欄はその文書にそのまま置き換える。

描画のあとで知らせる方式だと、知らせるまでのあいだは、保存の側の持つ文書と編集欄の文書が食い違う。その食い違いを「自分の編集」と取り違えると、他の人の行を消すコミットを送ってしまう。両者がいつも同じ文書を見ていれば、取り込んだ文書をもとに戻す計算も、取りこぼしも起きない。

### 画面

| 場面                                           | 挙動                                                                                                       |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 他の人の変更が届いた                           | 画面の文書を置き換える。カーソルと選択は、同じ行についていく。選択の始点の行が消されていたら、選択をやめる |
| 取り消しの履歴                                 | 他の人の変更が届くと消える(ADR-0017 から変わらない。取り消しを変更単位にするまで)                          |
| まだないページを開いていて、他の人が先に書いた | 表示していた仮のタイトルを捨てて、その人の内容を表示する。仮のタイトルは保存しない                         |
| 同じ行を2人が同時に書いた                      | あとからサーバーに届いたほうの本文になる(ADR-0016 の後勝ち)                                                |

## 理由(ユーザーストーリーから)

- **US-04**「他の人の編集が、再読み込みなしで1秒以内に反映される」: コミットは、保存した直後に配信する。自動テスト(2つのタブ)で、操作していない側の画面に反映されることを確かめた。
- **US-04**「別々の行への同時編集は、どちらも失われない」「全員の画面が最終的に同じ内容になる」: 応答と配信がどんな順で届いても、全員が保存し終えれば全員の文書がサーバーと一致することを、3つの端末を模したプロパティテストで検証した。
- **US-05**: 保存を HTTP に残したので、WebSocket がつながらない環境や、切れているあいだでも、保存は続けられる。そのあいだの他の人の変更は、自分の保存のときか、つなぎ直したときに取り込まれる。

## 検討した他の案

| 案                                                                    | 採用しなかった理由                                                                                                              |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 保存も WebSocket で送る                                               | 経路が1本になり、届く順序は単純になる。一方で、WebSocket が通らない環境では保存もできなくなる。再送や失敗の扱いも作り直しになる |
| 編集欄の状態を React の状態として持ち、描画のあとで保存の側に知らせる | 上の「いつも同じ文書を見る」のとおり。配信が続けて届いたときに、他の人の行を消してしまう不具合になった(レビューで判明)          |
| 送った本人にも配信し、識別子で照合する                                | 応答と配信のどちらが先に届いても正しく扱う処理が要る。配信しないほうが単純                                                      |
| 定期的に読み直す(ポーリング)                                          | 1秒以内に反映するには、全員が毎秒読みにいくことになる                                                                           |
| Server-Sent Events                                                    | Durable Object の休止に対応しているのは WebSocket。接続を保つあいだ、メモリに載り続けることになる                               |

## わかっている制約

- 取り消しの履歴が、他の人の変更が届くたびに消える。複数人で同時に書いていると、取り消しがほとんど使えない。次に、取り消しを「自分の変更を打ち消す」方式に置き換える(ADR-0014 で予定していたもの)。
- 同じ行を2人が同時に書くと、片方の入力が消える(後勝ち)。行の中の文字単位の統合は、実際の使い心地を見てから決める(ADR-0016)。
- 他の人のカーソルは表示していない。
- 接続が切れていることは、画面に出していない(保存の状態だけを出している)。
- 1つのページへの接続数に上限を設けていない。公開環境で有効にする(認証を入れる)ときに決める。

## 確認できていないこと

- Cloudflare 上での動作(休止、接続の維持、費用)。確認したのは、手元の Workers ランタイム(workerd)での自動テストだけである。
- 会社のネットワークなど、WebSocket を通さない環境での動作(保存は HTTP なので続けられる想定)。
