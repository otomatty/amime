# ADR-0022: 同じ行の同時編集を、文字単位で統合する

- 状態: 採用
- 日付: 2026-11-13
- 関連: [ADR-0016](0016-changes-and-line-ids.md)(同じ行の同時編集の扱いを、このADRで置き換える)、[ADR-0019](0019-undo-own-edits.md)(書き換えた行の取り消しの規則を、このADRで置き換える)、[ADR-0021](0021-commit-ids.md)(前提。復元でもう一度載せる変更の範囲を、このADRで置き換える)

## 状況

2人が同じ行を同時に書き換えると、あとからサーバーに届いたほうだけが残っていた(ADR-0016)。先に届いたほうの入力は、黙って消える。

ADR-0016 は、これを「実際の使い心地を見て見直す」としていた。箇条書きのメモでは、1行が長くなることも、2人が同じ行(たとえば議事録の同じ項目)を同時に触ることも珍しくない。書いたものが消えるのは、US-04 と US-05 の中心にある約束に反する。

## 決定

### 変更は、元にした本文を持つ

- 行の本文を置き換える変更(`update`)は、新しい本文(`text`)に加えて、**その変更を作ったときの行の本文**(`base`)を持つ。差分を求めるとき(`diffLines`)に付ける。
- 適用するときの規則は、次のとおり。サーバーでも端末でも、同じ規則で適用する。
  - 行の本文が `base` と同じ: `text` に置き換える(だれも先に書き換えていない)。
  - 行の本文が `base` と違う: だれかが先に書き換えている。`base`・いまの本文・`text` の3つから、文字単位で統合する。
  - `base` がない: `text` に置き換える(これまでと同じ)。
- 効いた変更(`applied`)は、**統合した結果への置き換え**として配る。`base` は付けない。受け取る側の確定した文書は、サーバーの適用前の文書と同じなので、そのまま置き換えれば同じ結果になる。

### 統合の規則

`base` から見て、いまの本文と `text` のそれぞれが「どの文字を消し、どこに文字を足したか」を求め、両方を合わせる。

| 場面                                                     | 結果                                                 |
| -------------------------------------------------------- | ---------------------------------------------------- |
| どちらかが消した文字                                     | 消える                                               |
| どちらかが足した文字                                     | 残る                                                 |
| 両方が同じ場所に、別の文字を足した                       | どちらも残す。先にサーバーに入っていたほうを前にする |
| 両方が同じ場所に、まったく同じ文字を足した               | 1度だけ足す                                          |
| 片方が消した範囲の中に、もう片方が足した                 | 足した文字は残る                                     |
| 片方が語を置き換え、もう片方がその語の直前や直後に足した | 足した文字は、置き換えた語の前や後ろに、そのまま付く |

- 文字の単位は、利用者から見た「1文字」(書記素)。絵文字や結合文字を、途中で切らない。`Intl.Segmenter` で決める(Workers のランタイムでも動くことを、サーバーのテストで確かめている)。
- 違いは、前後の同じ部分を除いたうえで、残す文字ができるだけ多くなるように求める。見比べる範囲が大きすぎるとき(元の文字数 × 変えたあとの文字数が100万を超える)は、その範囲をまるごと置き換えたものとして扱う。
- 統合した本文が1行の長さの上限(2万)を超えるときは、統合せず、あとから届いた本文にする。行が、送れない長さになるのを避ける。
- 1回の適用(1つのコミット)で統合に使える手間には、上限がある(見比べる本文の文字数と、細かく見比べる範囲の大きさの合計で200万)。超えた分は、統合せず、あとから届いた本文にする。ふつうのコミットは、この中に十分に収まる。1つのコミットにたくさんの統合を詰め込んで、サーバーの処理を長引かせることを防ぐ。

### カーソルは、同じ文字のそばに残る

- 他の人の変更を取り込んで、カーソルのある行の本文が変わったら、カーソルと選択の位置を、変わる前と同じ文字のそばに移す。手前に文字が足されればその分だけ後ろへ、手前の文字が消されればその分だけ前へ動く。
- ちょうどカーソルの位置に足された文字があれば、カーソルはその前にとどまる。

### 取り消し(ADR-0019 の置き換え)

- 自分が書き換えた行を、他の人も書き換えていた場合、これまでは取り消さなかった。これからは、**自分の変更だけを打ち消す**。打ち消す変更も `base`(自分が最後に書き込んだ本文)を持つので、上の規則で統合される。やり直しも同じ。
- ただし、自分が置き換えた文字を、他の人がすべて書き換えていたら、置き換える前の文字は戻さない(「b」を「B2」に書き換えたあと、他の人が行をまるごと書き換えた場合に、取り消しで「b」を足さない)。ふつうの統合は「足した文字は残す」が、取り消しで戻す文字は、いま入力したものではない。他の人が書き換えたところに、古い文字を戻す理由がない。
- 自分が足した行を他の人が書き換えていたら、消さない。これは変えない(その人の書いたものごと消してしまうため)。

### 端末内に残した変更の復元(ADR-0021 の置き換え)

- 記録が複数あるときに、今回の送り直しで入ったコミットをもう一度載せるのは、行の追加・削除・移動だけにする。本文の書き換えは載せない。順序によらず統合されるので、載せると足した文字が2重になる。
- `base` を持たない書き換え(このADRより前に残した記録)は、統合されずに置き換わる。これまでどおり、もう一度載せる。

## 理由(ユーザーストーリーから)

- **US-04**「同じページを同時に編集できる」: 同じ行を触っても、どちらの入力も残る。相手が行の前のほうに書き足しても、自分のカーソルは打っている場所からずれない。
- **US-05**「書いたものを失わない」: 通信が切れているあいだに書いた行を、他の人が書き換えていても、復帰したときに上書きも破棄もされず、統合される。
- 取り消し(ADR-0019)も編集の一種である。他の人が同じ行に1文字足しただけで、自分の編集が取り消せなくなることがなくなる。

## 検討した他の案

| 案                                                                           | 採用しなかった理由                                                                                                                                         |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 後勝ちのまま                                                                 | 上の「状況」のとおり。書いたものが黙って消える                                                                                                             |
| 文字ごとにIDを持つ(文字単位のCRDT)                                           | 行IDによる変更(ADR-0016)と保存の形(1行=1レコード)を作り直すことになる。行の中だけを統合すれば、いまの仕組みのまま、消えて困る場面のほとんどを救える        |
| 変更を「何文字目に何を足した」という操作で送り、サーバーで位置を変換する(OT) | 操作の順序と変換の正しさを、端末とサーバーの両方で保証する必要がある。本文と元にした本文を送る方式は、どの時点の文書に適用しても結果が決まり、検証しやすい |
| 統合できないとき(同じ場所への書き込み)は、利用者に選ばせる                   | 入力のたびに確認が出ると、書く流れが止まる。両方を残しておけば、あとで直せる                                                                               |
| 単語単位で統合する                                                           | 日本語は単語の区切りが明確でない。文字単位なら、言語によらず同じ規則で扱える                                                                               |

## 前提にしていること

- 同じコミットは、1度しか適用しない(ADR-0021)。統合は、同じ変更を2度適用すると、同じ場所に足した文字が2重になることがある。
- 端末は、サーバーと同じ規則で結果を予測して画面に出す。文字の区切り方がブラウザとサーバーで違っていた場合(Unicode の版の違い)は、予測がずれるが、サーバーの結果が届いた時点でそれに合わせる。全員の画面は同じになる。

## わかっている制約

- 統合した本文が1行の長さの上限を超えるとき、または、1回の適用の手間の上限を超えたときは、あとから届いた本文だけが残る。先に入っていた側が、そのあいだに足した文字は失われる(このADRより前の、後勝ちと同じ)。2万文字の行は、行を分けて書くべき量であり、2人の書き足しを合わせて初めて超える場面は、ごくまれだと考える。両方を残すには、1つの変更で行を2つに分ける仕組みが要る。必要になったら、そのときに決める。
- 2人が同じ場所に打った文字は、途中まで同じでも、それぞれの入力として残す(「は」と「はい」なら「ははい」)。共通する部分をまとめると、別々に打った文字を捨てることになる。まったく同じ文字を足した場合だけ、1度にまとめる。
- 2人が同じ単語を別々の語に書き換えると、両方の文字が混ざった本文になる(「猫」を「犬」と「鳥」に書き換えると「犬鳥」)。どちらも消えないが、意味は通らない。人が直す必要がある。
- 行を分けた・つないだ、という編集は、行をまたいで文字が動いたものとしては扱わない。行を途中で分けたのと同時に、他の人がその行の後ろのほうを書き換えていると、書き換えた文字は、分ける前の行に残る。
- 足した場所は、本文を見比べて推測する。同じ文字が並んでいる場所(「ああ」の途中に「あ」を足した、など)では、実際に打った場所と違う場所に足したものとして扱うことがある。結果の本文は同じ。
- 変更が元にした本文も送るので、本文を書き換える変更の大きさは、およそ2倍になる。
- 統合の計算には、上の「手間の上限」がある。上限いっぱいまで使うコミットで、手元の計測ではおよそ0.3秒かかった(ほとんどが、本文を文字に区切る時間)。
- 取り消しで戻るカーソルの位置は、編集したときの位置のまま。他の人がその行の手前を書き換えていると、少しずれる。
