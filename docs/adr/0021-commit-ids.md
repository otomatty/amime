# ADR-0021: コミットに識別子を付け、同じコミットを二重に適用しない

- 状態: 採用
- 日付: 2026-11-13
- 関連: [ADR-0016](0016-changes-and-line-ids.md)、[ADR-0017](0017-page-storage-and-api.md)(送信に失敗したときの扱いを、このADRで置き換える)、[ADR-0020](0020-pending-changes-on-device.md)(端末内に残す記録の形を、このADRで置き換える)

## 状況

送信に失敗すると、そのコミットがサーバーに入ったかどうかは分からない(応答だけが届かなかったのかもしれない)。これまでは、ページを読み直して、自分の変更をもう一度載せ直していた(ADR-0017、ADR-0020)。変更の適用は「同じ変更をもう一度適用しても、ほとんどの場合は何も起こさない」ので、これでおおむね正しく動いた。

しかし「ほとんどの場合」では足りない場面がある。

- 自分のコミットがサーバーに入ったあとで他の人が同じ行を書き換えていると、載せ直しが、その人の変更を上書きする。
- このあと、同じ行の同時編集を文字単位で統合する(ADR-0022)。統合は、同じ変更を2度適用すると、入力した文字が2重になる。

コミットが入ったかどうかを、**正確に**知る必要がある。

## 決定

### コミットにIDを付ける

- コミットを作るときに、送る側がID(乱数)を付ける。同じコミットを送り直すときは、同じIDを使う。
- `PageDO` は、受け付けたコミットのIDを覚えておく。同じIDのコミットがもう一度届いたら、何も適用せず、`duplicate: true` を付けて、いまのバージョンを返す。配信もしない。
- 何も効かなかったコミットのIDも覚える。覚えておかないと、送り直したときに、状況が変わっていて効いてしまうことがある。
- 覚えておくIDは、ページごとに新しいものから 10,000 件まで。

### 送信に失敗したとき

- 送信中のコミットを、そのまま持ち続ける。再試行では、**同じコミットを同じIDで送り直す**。
  - サーバーに入っていなかった: 今回の送信で入る。ふつうの応答が返る。
  - サーバーに入っていた: `duplicate` が返る。ページを読み直して確定した文書とし、そのあとに書き足した分を載せ直す。
- 送信中のコミットの行方が分かるまでは、自分の変更を「読み直したページに載せ直す」ことはしない。載せ直すのは、まだ1度も送っていない変更だけになる。
- サーバーが内容を断ったとき(400、413)は、入っていないことが分かっているので、送信中の状態をやめる(ADR-0017 のまま)。

### 端末内に残す記録(ADR-0020 の置き換え)

- 記録は、「送信中だったコミット(IDつき)」と「まだ送っていなかった変更」を分けて持つ。
- 次に開いたとき、次の順で復元する。
  1. 閉じたタブが残した記録を引き取る(ADR-0020 のまま)。
  2. 送信中だったコミットを、同じIDで送り直す。サーバーに入っていたら、何も起きない。
  3. ページを読み込む。送り直したコミットは、もう含まれている。
  4. まだ送っていなかった変更を、読み込んだページに載せる。
- 送り直しに失敗したら(通信できない)、ページの読み込みの失敗として扱う。もう一度読み込めば、同じ手順をやり直す。サーバーに断られたコミットは飛ばす。

## 理由(ユーザーストーリーから)

- **US-05**「通信が切れている間の入力は、復帰後に送信される」: 送信は「少なくとも1回」届けばよいのではなく、「ちょうど1回」効かなければならない。2回効くと、他の人の変更を上書きしたり、入力が2重になったりする。
- **US-04**「全員の画面が最終的に同じ内容になる」: 入ったかどうか分からないコミットを、推測で載せ直さなくなった。画面の文書は、いつも「サーバーが確定した文書に、まだ入っていないと分かっている変更を載せたもの」になる。

## 検討した他の案

| 案                                                       | 採用しなかった理由                                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| これまでどおり、読み直して載せ直す                       | 上の「状況」のとおり。同じ行の統合を入れると、入力が2重になる                                          |
| 読み直したページの内容から、入ったかどうかを推測する     | 他の人の変更が混ざると、見分けられない                                                                 |
| 応答に、適用したときの結果(効いた変更)を覚えておいて返す | コミットごとに変更の中身を保存することになる。重複だと分かれば、読み直せば足りる                       |
| IDを、送った端末の識別子と連番で作る                     | 端末の識別子はタブごとに変わる。端末内に残した記録を別のタブが送り直すので、コミットそのものにIDが要る |

## これで解消した制約

- 自分のコミットがサーバーに入ったあとで他の人が同じ行を書き換えていた場合に、再試行や復元で、その人の変更を上書きする。

## わかっている制約

- 覚えておくIDは 10,000 件までである。それより前のコミットを送り直されると、もう1度適用する。再試行は数秒から数分のうちに来る。端末内に残した記録の復元(最長30日後)でも、そのあいだにそのページへのコミットが 10,000 件を超えなければ、見分けられる。
- IDは送る側が作る。認証(P4)が入るまでは、送る側を信頼している。
