# ADR-0041: ミューテーションテストと、本番へ出したあとの画面の確認を入れる

- 状態: 採用
- 日付: 2026-11-15
- 関連: [ADR-0008](0008-tdd-and-ci.md)(カバレッジの限界と、ミューテーションテストの検討)、[ADR-0037](0037-ci-and-deploy-workflows.md)(Deploy)、[ADR-0039](0039-quality-gates-in-ci.md)(CI の検査)

## 状況

依頼者から、本番へ出す前に、CI で品質を担保したいという依頼があった(ADR-0039、ADR-0040 の続き)。

ADR-0008 は、純粋パッケージのカバレッジを 100% にしている。ただ、カバレッジは「実行された」ことしか示さず、「確かめられた」ことは保証しない。期待値を書き忘れたテストでも、100% になる。ADR-0008 は、その限界を埋める手段として、ミューテーションテストを検討するとしていた。

また、Deploy(ADR-0037)は、出したあとに `/api/health` が応えるかだけを見ている。Worker が応えても、画面の JS が読み込めない、開発用のログインが本番で有効になっている、といった壊れ方は分からない。

## 決定

### ミューテーションテスト

[Stryker](https://stryker-mutator.io/)(Vitest で動かす)で、`packages/*` の実装に、わざと小さな誤り(変異。`<` を `<=` に、条件を `true` に、など)を入れ、テストが落ちるかを確かめる。落ちれば「見つけた」、通れば「見逃した」。点は、見つけた割合。

| いつ                               | 対象                                     | 下限 | かかる時間(目安) |
| ---------------------------------- | ---------------------------------------- | ---- | ---------------- |
| パッケージの実装かテストを変えたPR | 変えたファイル(テストだけなら、その実装) | 80   | 数分             |
| 毎週(月曜 03:23 日本時間)と、手動  | すべてのパッケージ                       | 90   | 12分ほど         |

- ワークフローは `mutation.yml`。結果の表をジョブの概要に出し、見逃した変異の場所は HTML の報告(成果物、14日)で見る。
- 対象の選び方と、点の計り方は `scripts/lib/mutation.ts`(純粋関数、カバレッジ 100%)。
- 「すべての検査」(ADR-0039)には入れない。パッケージを変えないPRでは動かないため。ただし、動いたときに落ちたら、マージしない。

導入した時点(2026-11-15)の点は、全体で **93.1**(3013 の変異のうち、見つけた 2804、見逃した 209)。低いファイルは次のとおり。

| ファイル                        | 点   |
| ------------------------------- | ---- |
| `sync/src/merge-text.ts`        | 81.2 |
| `shared/src/invariant.ts`       | 83.3 |
| `editor-core/src/completion.ts` | 85.3 |
| `sync/src/own-edit.ts`          | 86.8 |
| `parser/src/rename.ts`          | 87.0 |

### 本番へ出したあとの画面の確認

Deploy の最後に、本番のURL(`APP_URL`)を Chromium で開く(`e2e/production`)。

- トップに名前とログインの案内が出る(画面の JS と CSS が読み込めている)
- 試し書きのページで、文字を打てる(エディタが動く)
- ログインしていないと、`/api/me` は利用者を返さない。開発用のログイン(`/api/auth/dev`)は使えない(ADR-0032)

ログインせず、読むだけにする。本番のデータは書き換えない。

## 理由

- ミューテーションテストは、カバレッジでは分からない「確かめていない分岐」を見つける。仕様の置き場所である純粋パッケージ(ADR-0008)に限れば、時間が現実的に収まる。
- 全体を毎回動かすと、PRごとに12分ほど増える。PRでは変えたファイルだけにし、全体は週に1回にする。
- PRの下限(80)は、いまいちばん低いファイル(81.2)より下に置く。いまのファイルに触れただけで落ちないようにするため。低いファイルは、テストを足して上げていく。
- 本番の画面の確認は、`/api/health` では分からない壊れ方(画面が出ない、設定の誤り)を、出した直後に見つける。開発用のログインが本番で有効になっていないことは、ビルドの段階でも見ている(ADR-0032)が、実際の本番でも確かめる。

## 他の案

- **ミューテーションテストを、毎回すべてに対して動かす**: 確実だが、PRの待ち時間が倍になる。
- **Stryker の差分モード(incremental)**: 前の結果を持ち越して、変えたところだけを動かす。結果の保存と受け渡しが要る。まずは、変えたファイルを選ぶ方法にする。
- **本番の確認で、ログインして書く**: 確かめられる範囲は広いが、本番に試験用のアカウントとデータが要る。Google のログインは自動にしにくい。

## 結果

- 毎週の全体の実行で、Actions の使用時間が、月に50分ほど増える。PRでは、パッケージを変えたときだけ、数分増える。
- 見逃した変異が209ある。点の低いファイルから、テストを足す(別の Issue)。
- 本番の画面の確認は、`APP_URL` を登録するまで動かない(docs/deploy.md の 4)。実際の本番では、まだ一度も動いていない。
